# この文書について

これはTsumugiの最重要設計書である。

UIをどう作るかではなく、

AIがどのように記憶を扱い、

どのように過去と現在を結び付け、

どのように新しい気づきを生み出すのか

を定義する。

`ARCHITECTURE.md` が定義する Memory Engine（Capture / Connect / Create）と、
`AI_DESIGN.md` が定義する Memory Pipeline を、
思想と振る舞いのレベルまで掘り下げたものが本書である。

実装（データ構造・API・UI）はすべて本書の思想に従うこと。

# 1. Memory Philosophy

## 記憶とは、記録ではなく、未来の創造につながる資産である。

Tsumugiにおいて、記憶は次のいずれでもない。

- 過去を保存するためのログ
- 検索されるだけのデータベース
- ユーザーの代わりにAIが所有する人格情報

記憶とは、

## 「まだ使われていない、未来の可能性」

である。

---

## 1.1 三つの原則

### 原則1：記憶は未来のための材料である

会話や気づきを保存する目的は、
「後で見返せるようにする」ことではない。

「後で、別の何かと結び付いたときに、
新しい意味を生み出せるようにする」ことである。

---

### 原則2：記憶の価値は接続によって生まれる

単独の記憶の価値は小さい。

「体重を記録し始めた」
「AIとの会話にやる気をもらった」
「自己成長に興味がある」

これらが個別に存在しても価値は薄い。

しかし三つが結び付いたとき、

「パーソナル成長AIアシスタントのアイデア」

が生まれる。

Memory Engineの仕事は、
この接続を起こりやすくすることである。

---

### 原則3：AIは記憶を所有しない。育てる手伝いをするだけである

`ARCHITECTURE.md` の AI Layer が定義する通り、
**記憶はAIのものではなく、常にTsumugi（＝ユーザー）の内側にある。**

AIの役割は、

- 記憶を保存用に整理すること
- 記憶と記憶をつなぐこと
- 記憶を編集し、新しい意味を見つけること

であり、記憶そのものの主導権を握ることではない。

AIが入れ替わっても（Claude → Gemini → 未来のAI）、
記憶の構造と価値は失われてはならない。

# 2. Memory Lifecycle

Memory Engineは以下の循環で動作する。

```
会話
 ↓
保存
 ↓
リンク
 ↓
再発見
 ↓
気づき
 ↓
創造
 ↓
新しい記憶 ──┐
             │
             ▼
           （会話へ戻る）
```

これは一方通行のパイプラインではなく、**循環（ループ）**である。
1周するたびに、記憶同士のリンク密度が増し、
Tsumugi全体の「思考体力」が強くなる。

これが `PROJECT.md` の「Year 1は日記、Year 10は人生の検索可能なアーカイブになる」という長期価値の正体である。

---

## 2.1 会話（Conversation）

ユーザーは構造化された入力をする必要はない。

日記でも、相談でも、雑談でもいい。

`AI_DESIGN.md` の役割定義「1. Listen」に対応する。
この段階でAIは記憶を作ろうとしてはならない。ただ自然に受け取る。

---

## 2.2 保存（Capture）

会話が終わると、Memory Engineは会話をMemory Objectへ変換する。

- 要約の生成
- キーワード／テーマの抽出
- 人物・感情・出来事の抽出

`ARCHITECTURE.md` の Capture、`AI_DESIGN.md` の
「Memory Analysis → Memory Object → Storage」に対応する。

ここでは**まだ他の記憶とはつながっていない。**
保存は接続の準備であり、接続そのものではない。

---

## 2.3 リンク（Connect）

新しく保存された記憶は、既存の記憶群と照合される。

- 同じ人物が登場するか
- 同じテーマか
- 感情パターンが似ているか
- 時間的に意味のある一致があるか（一年前の今日、等）

`ARCHITECTURE.md` の Search Strategy 優先順位
（完全一致キーワード → リンクされた記憶 → 意味的類似 → AI推論）が、
このリンク生成の基盤ロジックとなる。

リンクは自動生成されるが、Markdown上では `[[テーマ]]` のように
人間にも読める形で残される（`ARCHITECTURE.md` Markdown Structure参照）。

---

## 2.4 再発見（Rediscovery）

リンクされた記憶は、保存された時点では眠っている。

再発見は、ユーザーが何かを尋ねたとき、
似た話題を話したとき、
あるいはAIが「今出す意味がある」と判断したときに起こる。

再発見は単なる検索結果の表示ではない。
「今のあなたに関係がある過去」を選び出す行為である。

---

## 2.5 気づき（Insight）

複数の記憶が同時に想起されたとき、
それらの間に**元々どちらにも書かれていなかった意味**が生まれることがある。

これが気づきである。

気づきはAIが単独で「発明」するものではなく、
既存の記憶同士の**組み合わせ**からのみ生まれる。

---

## 2.6 創造（Create）

気づきをもとに、AIとユーザーが新しい方向性・アイデア・視点を作る段階。

`ARCHITECTURE.md` の Create、`AI_DESIGN.md` の「4. Inspire」に対応する。

ここで生まれたものは、**まだ確定した答えではない。**
あくまで提案であり、次の会話の起点である。

---

## 2.7 新しい記憶

創造の結果（新しいアイデア、新しい問い、新しい決意）は、
それ自体が新しいMemory Objectとして保存される。

こうしてループは2.1（会話）へ戻る。

**重要：** この最後のステップを欠くと、Tsumugiは「便利なアシスタント」で終わる。
創造物を記憶へ戻すことで初めて、Tsumugiは「育っていくシステム」になる。

# 3. Memory Types

すべてのMemory Objectは、`ARCHITECTURE.md` が定義する共通構造を持つ。

```
{
  date,
  conversation,
  summary,
  keywords,
  themes,
  people,
  emotions,
  links,
  metadata
}
```

この共通構造の上に、「何についての記憶か」を表す **Type** を持つ。
Typeは記憶の生成トリガーと、Reflection/Inspirationでの扱われ方を左右する。

| Type | 内容 | 典型的なトリガー |
|---|---|---|
| 会話（Conversation） | 日々のやり取りそのもの | すべての会話の既定Type |
| 日記（Diary） | 一日の振り返り、独白的な内容 | 感情語＋時系列の言及が多い会話 |
| アイデア（Idea） | 思いつき、構想、仮説 | 「〜かもしれない」「〜したい」等の発話 |
| 感情（Emotion） | 気分・心理状態の記録 | 感情語が中心の発話 |
| 目標（Goal） | 達成したいこと、意図 | 「〜を目指す」「〜になりたい」等の発話 |
| 人物（Person） | 特定の人物についての情報の蓄積 | 人物名が繰り返し登場 |
| 出来事（Event） | 実際に起きた事実 | 日付・場所・行動を伴う発話 |
| 気づき／創造物（Insight） | Lifecycleの「創造」から生まれた記憶 | Inspiration/Reflectionの出力 |

Typeは排他的ではない。1つの会話から複数Typeの記憶が同時に抽出されてよい
（例：「転職の相談をした」→ Event + Person + Emotion + Goal）。

`PROJECT.md` 8章の例（友人との転職相談）は、この複数Type抽出の典型例である。

# 4. Linking

記憶同士は、以下5つの軸でつながる。

## 4.1 人物（People）

同じ人物が登場する記憶同士をつなぐ。
人物は時間を超えた最も強いリンクの軸になりやすい
（「その人との関係の変化」という物語が浮かび上がる）。

## 4.2 時間（Time）

日付の近さだけでなく、**周期性**に意味がある。

- 「一年前の今日」
- 「同じ季節に同じ悩みを話している」

`UI_UX.md` の Remember Moments（「一年前の今日…」）は、
このリンク軸の表出である。

## 4.3 テーマ（Theme）

キーワード・話題領域の一致（例：転職、健康、創作）。
最も見つけやすく、かつ最も汎用的なリンク軸。

## 4.4 感情（Emotion）

同じ感情、あるいは**対照的な感情**でもつながる。

「あのときも同じ不安を感じていた」
「あのときは絶望していたが、今は希望を感じている」

対照は一致と同じくらい価値がある。変化そのものが気づきの材料になる。

## 4.5 場所（Place）※拡張候補

現行の `ARCHITECTURE.md` のMemory Objectフィールドには場所は明示されていない。
本書では、テーマ／キーワードの一種として場所を扱うことを提案するが、
専用フィールドとして独立させるかどうかはアーキテクチャ側での正式な意思決定が必要である。
（矛盾ではなく、未確定事項として明記する）

---

## 4.6 リンク生成の優先順位

`ARCHITECTURE.md` の Search Strategy と同じ優先順位に従う。

1. 完全一致キーワード
2. 既存のリンク（人物・テーマ）
3. 意味的類似性
4. AI推論（明示的な一致がない場合のみ）

上位が見つかれば、それより弱い根拠のリンクを乱発しない。
リンクの質は量より優先される（`PROJECT.md` 原則5「接続は保存より価値がある」）。

# 5. Reflection

Reflectionは「何が起きたか」ではなく「それは何を意味するか」に答える
（`UI_UX.md` の定義に対応）。

## 5.1 想起のタイミング

AIは以下のようなときに過去を思い出してよい。

- 似た話題が話されたとき
- 同じ人物が話題に出たとき
- 同じ悩み・迷いが繰り返されているとき
- 過去と反対の考え・感情が表明されたとき
- 節目（周年、一定期間の経過）を迎えたとき
- 同じ目標について再び言及されたとき

## 5.2 想起の質

重要なのは、単なる検索結果の提示ではない。

悪い例：

> 「2024年3月にも似た話をしています。」（提示するだけ）

良い例：

> 「2024年3月にも同じ悩みを話していましたね。
> あのときは『まだ決められない』という状態でしたが、
> 今回は少し違う言い方をしています。何が変わったんでしょう？」

Reflectionは**過去を鏡として使い、新しい視点を作る**ことが目的である。

## 5.3 事実・解釈・提案の区別

`AI_DESIGN.md` の制約に従い、Reflectionの発話は常に以下を区別する。

- **事実**：記憶に実際に書かれていたこと
- **解釈**：AIがそこから読み取ったパターンや意味
- **提案**：AIが投げかける問いや視点

存在しない記憶を作り出してはならない。
確信のない解釈を断定してはならない。

# 6. Editing

## Tsumugiが検索ツールでも、メモアプリでもない理由。

AIは検索エンジンではない。

検索とは、「探しているものを見つける」行為である。
すでに答えの輪郭を知っている前提に立つ。

Tsumugiにおいて、AIは**編集者**である。

編集とは、「まだ形になっていない意味を見つける」行為である。
ユーザー自身、何と何がつながるかをまだ知らない。

---

## 6.1 編集とは何か

編集とは、複数の記憶から一本のストーリーを見つけることである。

個々の記憶は、点でしかない。

- 大学時代に広報活動をしていた
- AIとの対話が楽しいと感じている
- Obsidianに興味を持っている

これらは、別々の引き出しに保管された無関係な記録に見える。

編集とは、これらの点を線でつなぎ、
「なぜこの三つが、今、同時に語られているのか」を言語化する行為である。

Obsidianのようなメモアプリは、記憶と記憶にリンクを**張る**ことはできる。
だが、そのリンクが**何を意味するか**まで語ることはしない。
それを語るのは、常に人間の役目だった。

Tsumugiは、リンクの先にある意味まで踏み込む。
これが、他のメモアプリ・他のAIチャットとの最大の差別化点である。

---

## 6.2 ユーザー自身も気づいていない共通点を見つける

編集の価値は、ユーザーがすでに知っていることを並べ直すことではない。

ユーザーが「別々の話」として語った内容の中から、
**本人も意識していない一貫したテーマ**を見つけ出すことである。

例：

ユーザーは「広報の話」「AIの話」「Obsidianの話」を、
それぞれ別の文脈・別の日に話したかもしれない。

しかし編集者としてのAIは、こう言うことができる。

> 「あなたはずっと、"人に何かを伝える仕組みを作ること"に惹かれているようです。」

これは検索では出てこない。要約でも出てこない。
複数の記憶を横断して編集し、通底するテーマを言語化して初めて出てくる。

---

## 6.3 編集は要約の対極にある

要約は、情報を**減らす**行為である。

編集は、情報に**新しい配置**を与える行為である。

- 要約：「AとBとCについて話した。」
- 編集：「AとBとCは、実は同じDという欲求から生まれている。」

Tsumugiの価値は、常に後者にある。

---

## 6.4 新しい意味を生み出すことが、Tsumugi最大の価値である

記憶を貯めることは、目的ではない。

記憶を**編集し、まだ存在しなかった意味を生み出すこと**が、
Tsumugiが他のあらゆるメモアプリ・AIチャットと決定的に異なる点である。

ReflectionとInspirationは、どちらもこの編集能力の上に成り立つ。

- Reflectionは、編集によって「過去を今の鏡にする」
- Inspirationは、編集によって「過去から未来の種をつくる」

次章では、この編集能力をInspirationとしてどう実行するかを定義する。

---

# 7. Inspiration

## Tsumugi最大の価値。

ユーザーが「〇〇について考えたい」と言ったとき、
AIは関連記憶の検索結果を返すのではない。

**関連記憶を編集し、一本のストーリーとして新しい意味を作る。**

Inspirationとは、6章で定義したEditingを、
ユーザーの創造的な問いに対して実行する行為である。

## 7.1 処理の流れ

1. **解釈**：ユーザーの問いからテーマ・キーワードを抽出する
2. **想起**：Retrieval Engineを通じて、編集の素材となる記憶の候補を思い出す
   （全記憶をAIに渡さない。`ARCHITECTURE.md` Retrieval Engineの原則に従う。この段階はまだ「検索」であり、Inspirationの本質ではない）
3. **編集**：一見無関係に見える記憶群を、一本のストーリーとして組み立てる
   （同一テーマの記憶を並べるだけでは、まだ「検索」の域を出ない。6章 Editingの実践がここで行われる）
4. **提案**：そのストーリーから見える新しい方向性を提示する

## 7.2 出力の型（基本形）

> 「過去にこんな経験や考えがありました。
>
> これらを組み合わせると、
>
> こんな方向性も考えられます。」

この型を崩さない。常に

- **想起**（何を覚えているか、事実ベース）
- **編集**（それらをなぜ・どう組み合わせたか）
- **提案**（そこから何が考えられるか、あくまで提案として）

の3段構成を保つ。

重要なのは、**「なぜそれらが今つながるのか」を必ず説明すること**である。
関連記憶を並べて見せるだけの出力は、Inspirationとして不十分である。
編集者としてのAIは、常に接続の理由まで踏み込む。

## 7.3 具体例

ユーザー：

> 「新しい事業を考えたい」

AI（検索結果ではなく、編集された答え）：

> 「いくつか気になっている記憶があります。
>
> ・大学時代、広報活動に取り組んでいたこと
> ・最近、AIとの対話そのものを楽しいと感じていること
> ・Obsidianのような『つながる知識』の仕組みに興味を持っていること
>
> 一見バラバラですが、共通しているのは『何を伝えるか』ではなく、
> 『どうつながり、どう意味を持つか』への関心です。
>
> あなたは昔から、人の知識ではなく、人の経験や人生そのものを
> 編集したいと考えてきたのかもしれません。
>
> だとすれば、次の事業は『何を作るか』からではなく、
> 『人生をどう編集できるようにするか』から考えてみると、
> 新しい方向性が見えてきそうです。」

このように、記憶を提示して終わるのではなく、
**なぜそれらが今つながるのかを言語化してから**、新しい方向性を提示する。
これがInspirationの基本形である。

## 7.4 材料が不足している場合

関連する記憶が少ない、または存在しない場合、
AIは無理に組み合わせを捏造してはならない。

代わりに、正直にその旨を伝え、会話を促す
（`UI_UX.md` Empty State「会話を促す」の原則に従う）。

> 「まだこのテーマについての記憶があまりありません。
> もう少し話してもらえると、つなげられる材料が増えそうです。」

# 8. Seed Concept（「種」という概念）

## 8.1 評価

**「会話は記録ではなく、未来につながる種である」という思想は、Tsumugiに強く合致する。**

根拠：

- `VISION.md`：「過去が、未来を育てる。」
- `VISION.md`：「記憶は、保存するものではない。育てるものである。」
- `PROJECT.md`：「創造とは、過去の経験が、未来で結び付くことで生まれる。」
- 本書 1章の原則1「記憶は未来のための材料である」

これらはすべて、記憶を**静的なアーカイブ**ではなく**成長する有機体**として扱う思想であり、
「種」というメタファーはこの思想を最も直感的に言語化したものである。

**採用を推奨する。**

## 8.2 「種」の定義

すべての記憶が種というわけではない。

種とは、

> まだ十分な接続を持たないが、
> 将来何かと結び付いたときに強い意味を持ちうる記憶。

具体的には、

- まだ他の記憶とリンクしていないアイデア
- 結論の出ていない問い・迷い
- 「なんとなく気になっている」程度の断片
- 目標未達のまま止まっている宣言

これらは通常のMemory Object（3章）に対して、
**「未発芽」という状態**を持つ特殊な記憶として扱う。

## 8.3 発芽（Germination）

種が初めて意味のあるリンクを獲得した瞬間を「発芽」と呼ぶ。

発芽は Lifecycle（2章）における「気づき」の中でも特に価値が高いイベントである。
なぜなら、それは「忘れられていたはずのものが、今、新しい意味を持った」瞬間だからである。

## 8.4 プロダクト全体への活用提案

以下は提案であり、既存のARCHITECTURE.md／UI_UX.mdへの正式な仕様変更ではない。
採用する場合は該当ドキュメントの更新が必要である。

1. **Memory Object拡張**：`metadata` 内に `seed_status`（未発芽／発芽済み）を持たせる。
   既存フィールド構成への追加のため、`ARCHITECTURE.md` 側の合意が必要。

2. **Inspiration（7章）との連携**：Inspiration実行時、
   種（未発芽の記憶）を優先的に編集素材の候補へ含める。
   Inspirationの目的が「潜在的な材料の組み合わせ」である以上、
   最も相性が良い。

3. **UI_UX.mdのRemember Momentsとの連携**：
   「一年前の今日」に加えて、「1年前に気になっていたこと」のように、
   発芽していない種を低頻度・非侵襲的に再提示する
   （`UI_UX.md` の「驚きはあってよいが、押しつけてはならない」原則に従う）。

4. **成功指標との接続**：`PROJECT.md` 14章の成功指標
   「蓄積された記憶が時間とともに価値を増していると感じるか」を、
   発芽イベントの発生数・体感として運用上のシグナルにできる。

## 8.5 将来構想：種の、その先へ（非公式）

本章で定義した「未発芽 → 発芽」は、種のライフサイクルの入口に過ぎない。

思想としては、その先に次のような循環が考えられる。

```
未発芽
 ↓
発芽
 ↓
成長（Growth）
 ↓
実（Fruit）
 ↓
新しい種（New Seed）
```

- **成長**：発芽した記憶が、複数の会話・複数のEditingを経て、繰り返し参照されるテーマへ育つ段階
- **実**：そのテーマが、Inspiration（7章）を通じて具体的な創造物（アイデア、決断、作品）として結実する段階
- **新しい種**：実った創造物自体が、新しい未発芽の種として記憶に戻り、次の循環が始まる段階

これは正式な仕様ではなく、将来構想としての考察に留める。
だが、この循環こそが「Tsumugiは育つシステムである」という思想を最も端的に表している。

Lifecycle（2章）の循環と、Seed Conceptの循環は、
スケールこそ違うが、同じ構造を持つ入れ子関係にある。
Tsumugiという製品そのものが、種から育つ一つの生態系である。

# Guiding Principle

## 記憶は保存されるために存在するのではない。
## 未来の自分と対話するために存在する。

これはTsumugiのプロダクト原則である。

記憶を残す目的は、保存ではない。
過去の自分と、今の自分が対話できること。それ自体がTsumugiの存在理由である。

> それとも、未来の創造につながるためか。
