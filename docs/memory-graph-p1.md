# Memory Graph P1：人物の文脈を会話に反映する

P1 は二つに分ける。

- **P1-A（このPR）**：人物の背景を組み立て、試験フラグで会話に渡す。保存は何もしない。
- **P1-B（次のPR）**：本人が確定した別名を Vault に保存する。

## なぜ分けるか

別名を Vault に保存するには新しいレコード種別が要る。種別は Markdown と `.tsumugi` が正、IndexedDB は再構築できる派生（STORAGE.md）。

その種別は保存基盤の全経路を通る：outbox、projection、起動時整合、復元、衝突処理、Export。
`CanonicalRecordType` を扱う非テストファイルは約23ある。

P1-A と同じPRに入れると、会話品質の変更と保存基盤の変更を同時に確かめることになる。そのため分けた。

P1-B が入るまで、会話は別名を使わない（`aliases` は空）。
人物シートの診断ページでは、画面上で「いっしょに表示」した名前を確定別名として扱い、会話に渡す背景をそのまま確認できる。保存はしない。

## P1-A の内容

### 1. 人物の背景（`src/lib/personContext.ts`）

P0 の人物シート（`personSheet.ts`）を軽量モード（`lite`）で使い、端末内で毎ターン組み立てる。

- AI呼び出し、保存、Memoryの変更はどれも無い。
- 各項目は、元のMemory ID と出どころ（本人の発言／AIの要約／候補）を持つ。

背景に含めるもの：

- **関係**：Capture の分類と、その根拠になった本人の言葉。
- **過去の考え・結論**：本人の発言の文を、文の形で分類したもの（`personStatement.ts`）。古い順。
  上限を超えたときは、結論を考えより先に残す。
- **後から本人が説明した理由**：次の三つを満たす本人の文だけを、前の結論の下に並べる。
  - 結論より後に言った
  - 理由の形（〜から／〜ので／〜ため／なぜなら／理由は）
  - 結論と内容語（漢字・カタカナ2文字以上）を共有する
  - 前の結論は消さない。
  - 理由として出した文は、単独では重ねて出さない。
- **AIの要約の解釈**：同じ内容語を持ち、理由の形をとる要約の文。本人の説明とは分けて表示し、違うかもしれないと明記する。
- **予定とその後の候補**：P0 の規則を使う。結果が無ければ「結果は不明」とする。
- **最近の出来事**：Retrieval がこのターンで既に渡したMemoryは除く。
- **最後に確認できた記録の日付**：「今」とは言わない。
- **名前の無い記録（候補）**：次の条件を両方満たすときだけ候補にする。
  - 強い根拠を一つ以上持つ：同じ会話、同じ話題、Connect のつながりのいずれか。
  - 根拠が合わせて二種類以上ある。共通の言葉も一種類として数える。
  - 本文が他の既知の人物名を含む記録は対象にしない。
  - 候補が判断の文なら、候補であることを明示したまま結論として扱い、後からの本人の理由を付けられる。

### 2. 人物の特定

このターンの人物は次の順で決める。

- 本人の今回の発言に出た名前。
- 今回の発言に名前が無ければ、直前2ターンの本人の発言に出た名前。
- 最大2人まで。

名前は人物シートのキー（敬称を除いて2文字以上。1文字なら敬称付き）で照合する。確定別名のグループは1人として数える。
似た名前、シートの推測、代名詞だけでは結び付けない。

### 3. 会話への接続

- フラグ：`?memoryGraph=1` で ON、`?memoryGraph=0` で OFF。既定は OFF（`memoryGraphFlag.ts`）。
- ON のとき、ChatScreen は読み込み済みのMemory一覧から背景を作り、`personContext` として送る。
  - 背景に含まれる人物の PersonView は二重に送らない。
- route は受け取った内容を再検査し（`personContextPrompt.ts`：形、件数、長さ、候補の根拠2種）、システム指示に1節だけ加える。
  - 指示の要点：
    - 過去の考えを今の事実として扱わない。
    - 本人の後からの説明を AI の解釈より優先する。ただし新しいというだけで以前の本人の言葉を否定しない。
    - 候補は確定しない。
    - 必要なときだけ使う。
- OFF のとき、または背景が空のとき、プロンプトは従来とバイト単位で同じ。
- 背景を作る処理が失敗しても空配列になり、会話は止まらない。

### 上限（`PERSON_CONTEXT_LIMITS`）

| 項目 | 上限 |
| --- | --- |
| 人物 | 2 |
| 結論・考え | 6 |
| 後からの理由（1結論あたり） | 2 |
| AIの解釈（1結論あたり） | 1 |
| 予定 | 2 |
| 出来事 | 3 |
| 候補 | 2 |
| 1文の長さ | 160字（超える文は途中で切らず、丸ごと外す） |

## テスト（`npm run test:person-context`、架空データ）

- 別名：確定したときだけ1人になる。未確定なら、もう一方の名前の記録は入らない。
- 名前の無い記録：
  - 共通の言葉だけ（弱い根拠のみ）なら結び付けない。
  - 同じ会話だけでも結び付けない。
  - 他の人物名を含む記録は結び付けない。
  - 進行中の会話を除くと、根拠が無くなる。
- 三つを分けて保つ：
  - 前の結論は残る。
  - 後からの本人の理由は、その結論の下に付く。
  - AIの解釈は、本人の説明とは別に表示する。
- 旧（PersonView）との比較：
  - 旧は名前の無い結論ともう一方の名前に届かない。新は届く。
  - 無関係なMemoryは増えない。
- 人物の特定：
  - 名前が無ければ背景は無い。
  - 直前2ターンまでは持ち越す。
  - 背景が空なら節は空文字。
- 出来事：Retrieval の重複を除く。予定の結果が不明なら「不明」と出る。
- 上限：多数の考えがあっても、古い結論は残る。
- route の再検査：
  - 不正な形、長すぎる文、根拠1種の候補は外す。
  - AIの解釈を名乗る本人発言は外す。
  - 人物は2人まで。
- 速度：Memory 1,500件で1ターン3秒未満（CI）。

## 未検証

- 実際の AI の応答の質（自然さ、過去の持ち出し方）。フラグ ON の実機会話での確認が必要。
- 実データでの候補の当たり外れ。人物シートの診断ページの「会話に渡す背景」で確認できる。

## P1-B：確定別名の Vault 保存（設計案）

- **保存先**：`People/` に人物ごとの Markdown を置く。VAULT_DIRS に既にあり、未使用。
  - 本文は人が読める別名の一覧。
  - 機械用データは `.tsumugi` 側に置く。
- **記録の形**：追記のみ。
  - 「確定」「取り消し」を1件ずつ日時付きで残す。
  - 現在の別名は、それを順に畳み込んで得る。
  - 取り消しと訂正ができる。履歴は消さない。
- **Memory は書き換えない**：別名は会話と人物シートで名前を束ねる時だけ使う。
- **保存経路**：新しい `CanonicalRecordType`（例：`person-alias`）として、既存の経路をすべて通す。
  - outbox → projection → 起動時整合 → 復元 → 衝突処理 → Export
  - IndexedDB は派生で、Vault から再構築できる。
- **確定の操作**：人物シートの別名候補から、本人が明示的に確定したときだけ。自動では結合しない。
- **順序**：
  1. 保存基盤への種別追加を、テスト付きの単独PRにする。
  2. 確定・取り消しの UI。
  3. 会話の `aliases` への接続。
