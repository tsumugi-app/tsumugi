# Memory Graph P1-B：人物の別名の確定と Vault 保存

本人が「同じ人物」と確定した名前だけを1人として扱う。確定は Vault の `People/` に保存し、人物シート・会話の人物背景（P1-A）・Retrieval で同じように使う。

- 自動では結合しない。名前の推測・似た名前・部分一致では束ねない。
- Memory の本文・personMentions・keywords は書き換えない。
- AI 呼び出しは無い（端末内のみ、AI の種類に依存しない）。

## 操作（人物シートの診断ページ）

- 既存の「いっしょに表示」の候補から、「これらを同じ人物として確定する」を押す。
  - 確定の前に、束ねる名前を一覧で示して確認する。
- 「同じ人物として確定した名前」の欄で、確定済みの名前を一覧し、「この名前を外す」で取り消せる。
- 拒否する場合（理由を表示する）：
  - 名前が1つだけ、または敬称を除くと同じ名前。
  - 別々の人物に属する名前どうし（2人を1回で結合しない。先に一方を外す）。
  - 既に確定済み。
  - 競合している名前（2台の端末で別々の人物に確定された名前）。競合した名前はどちらの人物にも入れず、ページに表示する。
- 名前の照合は人物シートのキー（`personSheetKey`：幅・空白・敬称を除く。1文字なら敬称付き）が完全に一致するときだけ。

## 保存方式

| 場所 | 内容 | 役割 |
| --- | --- | --- |
| Vault `People/<名前> (<id末尾6桁>).md` | 人物1人につき1ファイル。frontmatter（id・type: person・displayName・aliases・作成/更新日時）、読める履歴、確定/取り消しの記録（JSON1行、HTMLコメント内） | **正（source of truth）** |
| IndexedDB `settings` ストア、キー `people:v1` | Vault の写しと、この端末でまだ Vault に書けていない決定（`pending`） | 派生。消えても次の同期で Vault から作り直す |

- 記録は**追記のみ**。「確定」「取り消し」を1件ずつ id・日時付きで残し、現在の名前はそれを順に畳み込んで得る。訂正は「取り消し→確定」。履歴は消さない。
- 2つの写し（2台の端末、Vault と端末）は、決定の和集合（id 単位）でまとめる。順序に依存せず、決定は失われない。
- IndexedDB のバージョンは上げない（既存の `settings` ストアを使う）。
- バックアップ／Export：`People/*.md` は既存の Vault バックアップの対象（`isBackedUpVaultPath`）。端末の写しも `settings` ストアとして端末スナップショットに入る。

### Registry / outbox を使わない理由

- 配布済みのどのビルドも、Registry の検証が未知のレコード種別を拒否する。その場合、シャード全体を読めないものとして扱う。人物の行を入れると、古いビルドの別端末が壊れる。
- outbox の利用側（状態表示・整合チェック・メンテナンス）は、全エントリを Conversation / Memory / Source として数える。人物を入れると誤った分類になる。
- 人物は少数なので、`People/` を直接読む。保存基盤のレコード経路には一切触れない。

## 同期（起動時、`syncPeopleWithVault`）

アプリ起動時、保存基盤の起動処理（`runSaveFoundationBootstrap`）の直後に、他の保存と同じ Vault 保存ロック（`withVaultSaveLock`）の中で実行する。修復・復元・他の保存とは同時に動かない。タブ間は Web Lock `tsumugi-people-sync` でも1つずつ。失敗しても例外を投げず、決定は端末に残って次回の起動で再試行される。

1. Vault がこの端末とペアリング済みのもの（`.tsumugi/vault-identity.json` の vaultId が一致）で、修復・メンテナンス中でないこと。違えば何も読まず、何も書かない。
2. `People/*.md` をすべて読む。人物ノートとして丸ごと読めないファイルは上書きしない（名前を報告する）。
3. 人物ごとに、端末の写しと Vault の写し（同期ツールの競合コピーも含む。削除しない）の和集合を作る。
4. Vault に無い決定があれば書く。
   - 書き先：アプリが書いてから誰も編集していないこの人物のノート（丸ごと置き換える）。
   - 手で編集されたノート・他のファイル・同名の別ファイルには書かない。隣に新しいファイル名で書く（読み手が id で統合する）。
   - フォルダを最後まで列挙できなかったときは書かない。
   - 書いたあと読み戻し、すべての決定を含むときだけ `pending` を消す。
5. 端末の写しにあり、Vault に無く、`pending` も無い人物は、Vault で削除されたものとして端末からも消す。`People/` を完全に読め、読めない人物ノートが1つも無いときだけ（手で壊したノートで人物が消えないように）。
6. 端末の写しを1トランザクションで更新する。その間に行われた決定もあわせてまとめ直す。

診断ページでの確定・取り消しは、判定と記録を1トランザクションで行い（別タブの同期で状況が変わっていても、その時点の内容で拒否を判定する）、まず端末に保存する（`pending`）。Vault には次の起動時に書く。診断ページはワールドロックやタブの世代を持たないため、ページから直接 Vault には書かない。

## 会話・Retrieval への反映

試験フラグ `?memoryGraph=1` のときだけ使う。OFF のときは従来と同じ。

- ChatScreen は毎ターン、端末の写しから確定した名前の組（`loadConfirmedAliasLists`）を読む。読めなければ空で、従来どおり。
  - Retrieval（`personAliases`）と、人物背景（P1-A の `aliases`）に渡す。
- Retrieval（`selectConversationWithPersons`）：
  - 組の名前は同じ人物として数える。両方の名前が出ても「2人」にしない。
  - 組のどの名前の記録も、その人物の記録として扱う。各 Memory は1回だけ。
  - 組に含まれない名前の記録は、従来どおり別の人物として外す。
  - 使う組は、既知の名前を1つ以上含み、キーが2つ以上あるものだけ。
- 取り消した名前は組から外れ、元の別人物の扱いに戻る。
- 未確定の候補は、会話で同じ人物として断定しない（組に入らない）。

## テスト（架空データ）

`npm run test:person-alias`、`test:retrieval-person`、`test:vault-backup` に追加した。

- 規則：
  - 確定すると1人になる。取り消すと戻る。訂正（取り消し→確定）ができ、履歴は残る。
  - 名前1つ、同じ名前、別の人物どうし、確定済みは拒否する。
  - 部分一致・似た名前（まりこ／りこ）は結合しない。
  - 競合した名前は除く。
  - 和集合のマージは順序に依存しない。
- Markdown：
  - 往復で同じ内容に戻る。
  - 丸ごと読めないノートは `null` になる（上書きしない）。
- 同期：
  - `pending` → 書き込み → 読み戻し → 解除。再起動しても残る。
  - 書き込み失敗、途中までしか書けない、ペアリング不一致のときは `pending` のまま残る。
  - IndexedDB が消えても Vault から復元できる。
  - 2台の端末の和集合をとり、競合コピーは残したままマージする。
  - Vault で削除された人物は、完全に読めたときだけ端末から消す。
  - 手で編集したノート、同名の自分のメモは上書きしない。列挙に失敗したら書かない。
- Retrieval：
  - 確定すると両方の名前の Memory が入り、重複は無い。
  - 未確定では入らない。
  - 組が空や無効なら、選定は完全に同じ。
  - 持ち越し（carried）でも組を保つ。
- 人物背景：確定なら1人、未確定なら2人。
- バックアップ：`People/*.md` がバックアップの zip に入る。
- 配線：
  - Memory の書き込み・AI・outbox・registry に触れない。
  - 会話はフラグ ON のときだけ読む。
  - 起動時同期は保存基盤の後に行う。

## 既知の限界・未検証

- 名前の文字列がキーなので、**同じ名前の別人**は区別できない（同じキーは常に同じ名前として扱う）。結合は本人が明示的に選んだ組の完全一致だけで、自動では起きない。
- 診断ページで確定した内容が Vault に書かれるのは、次のアプリ起動時。それまでに端末のデータが消えると、その決定は失われる。
- 実機（Android / iPhone / PC の実際のフォルダ）での同期、同期ツールの競合コピーの実際の名前の付き方：未検証。
- 実際の AI の応答で、確定した別名の扱いが自然か：未検証（フラグ ON の実機会話での確認が必要）。
